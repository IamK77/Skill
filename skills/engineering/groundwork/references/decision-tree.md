# Ask only what changes the work

## Use when

Use the ambiguity in the request and the person or source authorised to resolve it.

## Method

If the outcome is clear, record a concrete acceptance example and proceed. If reasonable implementations would disagree about user-visible behaviour, ask the smallest clarifying question that distinguishes them. If the human wants possibilities, offer an appropriate heuristic rather than prematurely creating a fixed specification.

## Example and record

'Add export' may be clear about format but unclear about which records a caller can include. Ask about the permission boundary before choosing an API shape. Conversely, a typo correction rarely needs a full discovery exercise.

## Limits and handoff

Architecture and product scope can overlap; make assumptions visible and identify who decides. An unanswered material question is a blocker or an explicitly deferred decision, not permission to fill in a requirement silently.
